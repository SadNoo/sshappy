# 4.4.0 release notes and explicit deferrals

Version 4.4.0 is an accounting-durability and deployment-safety release based on the immutable 4.3.1 baseline. It deliberately avoids changing SSPanel quota or speed-limit business semantics.

## Completed in 4.4.0

- **SQLite WAL outbox:** traffic capture and removal are transactional and no longer rewrite a complete JSON queue. The connection uses WAL mode, full synchronization, foreign keys and a bounded busy timeout.
- **Frozen billing context:** every durable batch stores the capture-time node ID and canonical traffic rate. A delayed replay cannot silently adopt a different node/rate.
- **Payload validation:** canonical batch data is hashed with SHA-256 and validated from durable storage before replay/deletion. Corruption and unsafe file replacement fail closed.
- **Private single-writer state:** a lifetime state-directory inode lock plus a visible per-outbox file lock reject a second writer, including after `.lock` pathname replacement. New outbox directories/files use private Unix modes; unsafe existing permissions, symlinks, hard links, orphan sidecars and unsupported formats are rejected without modifying operator-owned state. An atomic marker recovers interrupted first-time initialization.
- **Bounded database work:** runtime MySQL calls use explicit context deadlines, normal cycles replay no more than 64 durable batches, and final shutdown captures current counters before attempting remote replay.
- **Checked billing arithmetic:** raw, rated, aggregate and duplicate-user totals that exceed `int64` fail instead of wrapping into incorrect accounting values.
- **Explicit MySQL migration:** the runtime no longer executes DDL. Migration version/name and the required InnoDB table definitions are validated at startup.
- **Release packaging:** each binary archive and Docker image contains `migrations/mysql/0001_traffic_batch.sql` from the release tree.
- **Rollback boundary:** 4.3.1 JSON is preserved rather than converted or overwritten, and the required drain/backup/sequential upgrade procedure is documented.

The 4.3.1 authorization hardening remains unchanged: strict rule compilation, domain final-IP enforcement, bounded UDP resolution pinning, active session revocation, backlog capture and aggregate UDP failure logs.

## User-visible differences

- A fresh 4.4 deployment creates `traffic-outbox.sqlite3` plus transient WAL/shared-memory sidecars instead of `traffic-outbox.json`.
- The state directory also contains a persistent `.lock`; a transient `.init` appears only while first-time initialization is incomplete. Starting a second writer fails explicitly.
- Upgrading without draining the old JSON queue or without applying the MySQL migration fails startup with a diagnostic instead of mutating state or attempting DDL.
- Traffic delayed in the local queue retains the node ID/rate that applied when it was captured. This differs from 4.3.1, which applied the node/rate current at flush time.
- Operators can run the long-lived runtime account without table-creation privileges after a separate migration account has prepared the schema.
- Relay behavior and valid low ports are otherwise unchanged; examples use port 1023 over TCP and UDP.
- A large recovered backlog is drained incrementally so MySQL work cannot indefinitely block policy refresh; any remainder stays durable.

## Explicitly deferred

4.4.0 does not enforce real-time quota from pending local traffic and does not enforce the loaded node/user speed-limit fields. A safe implementation needs product decisions for:

- global versus per-node quota and multi-node reservation/fencing;
- raw versus rated bytes, reset/top-up timing, outage overshoot and session-close behavior;
- speed units, zero/null meaning, node/user hierarchy and TCP/UDP sharing;
- combined/separate directions, burst capacity, queue/drop behavior and hot updates.

Until that contract exists, the current fail-closed accounting grace limits exposure but is not advertised as exact distributed quota enforcement.

## Release and rollback references

- development branch: `4.4`;
- release tag: `v4.4.0`;
- images: `sadno/sstest:4.4.0` and `sadno/sstest:4.4` from one verified digest;
- immutable rollback baseline: branch `4.3.1`, tag `v4.3.1`, image `sadno/sstest:4.3.1@sha256:fd8a3091597a3aff699ea51e254477781f6927493f38cf3814b6067aff09dfe6`.

Do not publish `latest`, overwrite a version-specific image tag, move a release tag, or run two versions against one state directory. A real Debian 11 amd64 host still requires production acceptance testing; the image itself uses Debian 12 distroless/static userland and targets Docker Engine on Debian 11+ hosts.
