# 4.3.1 remaining work and explicit deferrals

Version 4.3.1 is a focused hardening patch based on the immutable `v4.3.0` rollback baseline. It closes high-confidence issues that do not require a mandatory database migration or an invented SSPanel business rule, while keeping unresolved work explicit.

## Completed in 4.3.1

- **Final resolved-IP enforcement**: TCP and UDP domain targets are checked against the authenticated user's `forbidden_ip` policy after resolution, using the final IP selected for the outbound connection. UDP sessions use a 64-domain bounded cache and pin each first resolution to avoid per-packet DNS amplification and rebinding.
- **Strict user policy parsing**: invalid `forbidden_ip`, `forbidden_port` and `disconnect_ip` entries fail closed for their owning user instead of being silently ignored; unrelated valid users continue to operate.
- **Active session revocation**: removing a user, invalidating or changing its security policy, or rotating its password/key cancels its registered TCP and UDP sessions without waiting for their natural timeout.
- **Durable traffic during a database backlog**: when an existing backlog cannot be flushed, newly captured traffic is appended to the compatible outbox before the reporting cycle returns the database error.
- **Aggregated UDP decryption logging**: decryption failures are counted and reported periodically rather than emitting one warning for every rejected packet.
- **Release workflow repository and immutability fix**: every `gh release` operation addresses `${GITHUB_REPOSITORY}` explicitly, and the workflow no longer overwrites existing release assets with `--clobber`.

## Security and authorization

- **Credential-generation fencing**: 4.3.1 cancels registered sessions when a password/key revision changes, but the authenticated credential generation is not carried from the SS2022 handshake into session registration. A future protocol-level extension could provide an absolute fence for the narrow handshake/refresh race.
- **Quota during accounting outage**: SSPanel eligibility uses committed database counters. The fail-closed accounting deadline bounds the outage, but traffic held in the outbox or in transit is not deducted from authorization queries during that grace period, so a user may temporarily exceed quota. Exact enforcement requires loading an explicit remaining quota and reconciling local pending bytes without double subtraction.
- **Speed limits**: node/user speed-limit fields are loaded but are not enforced. Token-bucket units, burst behavior, hierarchy and hot-update semantics need an explicit product contract before implementation.

## Accounting and storage

- The advisory lock serializes concurrent processing of one batch. Automatic marker cleanup is disabled by default because a local process cannot know about another host's old outbox; a future schema should model batch/chunk state explicitly so cleanup can use a proven safe watermark across hosts.
- The JSON outbox rewrites the full queue for each capture/removal and has no hard batch, byte or age bound. A WAL or SQLite queue with compaction and a documented backpressure policy is preferable for long database outages.
- `OUTBOX_MIN_FREE_BYTES` remains primarily an operational warning threshold; it is not yet a complete admission-control policy.
- Startup still creates the idempotency table when absent. Versioned migrations and startup schema compatibility checks should replace runtime DDL before a least-privilege production rollout.

## Runtime and performance

- Online last-seen is refreshed when a connection/session or source address is observed, not continuously for a stable long-lived flow. Activity should be touched from successful traffic with rate limiting.
- Most panel database methods still use driver timeouts rather than per-operation contexts and deadlines, and the main scheduling loop performs database tasks serially.
- UDP decryption failures now use periodic aggregate logging, but session maps still retain coarse relay-level critical sections and other malformed-input paths need continued load testing.
- DNS fallback/stale-cache semantics, multi-address routing policy and RFC 2308 SOA minimum handling remain separate correctness improvements.

## Platform, container and deployment

- Non-Unix credential confidentiality still depends on deployment-provisioned filesystem ACLs. Native Windows packaging should add and test an explicit private-DACL policy before being treated as production-ready.
- The `linux/amd64` 4.3.1 image has a restricted build context, pinned Debian distroless/static runtime, explicit privileged-port behavior, an optional non-root user and documented persistent-state strategy. Automated image signing remains deferred pending a release policy.
- The image uses Debian 12 userland and is intended for Debian 11+ Docker hosts, but the full TCP/UDP/plaintext-MySQL/graceful-shutdown acceptance test still needs to run on a real Debian 11 amd64 host before that compatibility claim is treated as production-certified. The acceptance port is 1023 for both TCP and UDP.
- Local validation on macOS cannot execute Linux `sendmmsg`, tproxy or the real MySQL integration path. Linux race and disposable-MySQL CI results must be checked for the final release commit.

Preserve the `4.3` branch, `v4.3.0` tag and their recorded Docker image digest as the first rollback target. Also preserve the 4.2 binary and configuration as the older fallback. Version 4.3.1 retains the exact 4.2 outbox JSON fields, wrapper version and flush-time billing semantics so a stopped 4.3.1 process's durable queue can be opened sequentially by 4.3.0 or 4.2 without conversion. Never let two versions write the same state directory concurrently.
